Map · Part I · Classic Go Map (Go < 1.24)

一、经典 Go Map（hmap + bmap）：拉链分桶与渐进搬迁

Go 1.24 之前的经典内建 map 采用“哈希数组 + 每桶 8 槽位 + 溢出桶链表”的设计。通过把 key[] 与 value[] 分层紧凑存放节省内存对齐开销，并用 tophash 字节数组加速过滤与标记搬迁状态。

空闲 / 未初始化槽位 有效数据 / 命中高亮 扫描指针 / 哈希计算 警报 / 对齐空洞 / 锁 / 墓碑 溢出桶 / 指针 / 新数组 tophash / ctrl 元数据
Map · Part II · Concurrent Safe sync.Map

二、并发安全 sync.Map：读多写少场景下的双表无锁魔法

普通 map 并发读写会直接触发 fatal error，而粗粒度 RWMutex 在高核数读场景下仍会因修改 readerCount 引发严重的缓存行争抢。sync.Map 通过 read 只读快照表 + dirty 加锁脏表 + 共享 *entry 盒子实现读多写少的极致无锁吞吐。

read 无锁高速读 / 命中 共享 *entry 指针盒子 原子 CAS / misses 计数 mu 互斥锁 / amended 红灯 / expunged 印章 nil 软删除 / 空表
Map · Part III · Go 1.24+ Swiss Table

三、Go 1.24+ Swiss Table：SWAR 并行探测与可扩展哈希局部裂变

Go 1.24 正式将底层 map 升级为源自 Google Abseil 的 Swiss Table 架构：彻底告别伤缓存的溢出桶链表，改用连续内存的 8 槽位 Group + 64 位控制字 ctrl，靠一次 SWAR 位运算并行查 8 格，并结合可扩展哈希（Extendible Hashing）把大表拆成 ≤1024 槽位的小表实现微秒级局部裂变。

64 位 ctrl 元数据 / SWAR 激光束 有效数据 (0xxxxxxx · h2 指纹) 空槽 ctrlEmpty (0x80) 墓碑 ctrlDeleted (0xFE) 三角形探测步长 (+1, +2, +3…) Directory 目录 / 裂变小表

三种 Go Map 底层架构全景对比

Go Map Evolution · Comparison
数据结构 核心内存布局 冲突解决 & 探测方式 扩容机制 最佳适用场景
经典 Map
Go < 1.24		 hmap + bmap 数组；每桶 8 槽位按 tophash / keys / vals 三层紧凑存放 拉链法（overflow 溢出桶链表）；顺序扫描 8 格 tophash 装载因子 > 6.5 翻倍增量扩容，或溢出桶过多触发等量压缩；写入时渐进搬迁 Go 1.24 之前的通用单协程哈希表（并发读写需自行加锁）
sync.Map
标准库并发		 无锁只读 read 表 + mu 加锁 dirty 表 + 双方共享 *entry 指针盒 读先查 read（原子加载），未命中且 amended=true 才加锁查 dirty misses == len(dirty) 时 dirty 一键转正替换 read；删键分 nil / expunged 读多写少、Key 集合相对稳定、高核数并发读取（写多场景反不如分片锁）
Swiss Table
Go 1.24+		 顶层 Directory 目录 + ≤1024 槽位连续小表；每 Group 含 64 位 ctrl + 8 槽位 开放寻址 + 三角形探测（+1, +2, +3…）；SWAR/SIMD 一次并行查 8 格，墓碑 0xFE 保链 可扩展哈希局部裂变：满表时仅拆分单张小表并更新目录指针，微秒级无大停顿 Go 1.24+ 默认内建 map，高缓存命中率、更快查询/迭代与更平滑扩容
